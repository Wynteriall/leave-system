Progress report · November 2026

Employee Leave Management System

From a general project idea to a clear plan for a working system.

Current statusWe have completed the planning and design foundation. We are ready to begin building the first working version.
01 · Context

We first needed to understand the process before building it.

The project aims to replace paper-based leave applications with a system where employees can submit requests, managers can review them, and administrators can manage the records and rules.

Before creating screens, we focused on one practical question: how should a leave request move through the system, and how can we make sure that only the right people can view or change it?

02 · Progress

We clarified the parts that were still open.

1

Responsibility is clearer.

We added a manager role so requests can be reviewed by the person responsible for the employee’s team. The administrator manages the system and handles exceptional cases.

2

The complete request journey is planned.

We considered what happens before submission, during review, after approval or rejection, and when a request needs to be cancelled or corrected.

3

Privacy and accountability are part of the design.

Employees should only see their own information. Managers should see what they need to make a decision. Approvals, rejections, and important changes should remain visible.

4

The build direction is agreed.

We chose a practical web application approach that matches our experience and keeps the project manageable to build and demonstrate.

RoleMain responsibility
EmployeeSubmit and track personal leave requests.
ManagerReview and decide on requests from the team.
AdministratorManage users, leave rules, records, and exceptions.
03 · Evidence

Our progress is the foundation for implementation.

The working application has not been built yet. The completed work at this stage gives the team a shared understanding of what to build, why it matters, and what should happen first.

Completed during this phase

  • User responsibilities have been agreed.
  • The complete request and decision process has been mapped.
  • Privacy and security concerns have been identified.
  • The information needed for leave records has been organized.
  • The technology direction and build order have been chosen.

Not completed yet

  • The working application.
  • Final screens and user testing.
  • The end-to-end demonstration.

Why this progress matters

Starting with a shared process reduces the risk of building disconnected screens or making security decisions too late. The next phase can focus on implementation instead of changing the project direction.
